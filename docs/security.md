# Security

Plain English. No legalese. This page explains how Hausbuch is scanned,
how to report something we missed, what we have and have not protected
in the hackathon build, and where the proof of the scan lives.

## How Hausbuch is scanned

Hausbuch is continuously scanned by [Aikido](https://www.aikido.dev),
linked directly to this GitHub repository. Every push to `main` triggers
a scan that covers:

- application source (SAST)
- production npm dependencies (SCA)
- container and IaC config if present
- secret patterns in committed code
- known-vulnerable license and supply-chain signals

Aikido is the source of truth. As a local backstop, the
`.github/workflows/security.yml` GitHub Action runs `npm audit` on
production dependencies for every push and pull request to `main` and
fails the build on **high** or **critical** advisories. That action is
deliberately small — it is not a substitute for Aikido, just a guard
against a vulnerable dep slipping in between SaaS scans.

The latest scan screenshot lives at `docs/security/aikido-scan.png`.
That file is dropped in by hand before each submission tag; it is not
generated by CI and is not committed as part of normal development.

## Disclosure policy

If you find a security issue in Hausbuch, please email
**security@hausbuch.dev** with:

- a short description of the issue
- steps to reproduce (or a proof-of-concept)
- the commit hash or deploy URL where you observed it
- whether you would like to be credited if we publish a fix

Our commitments:

- **Acknowledgment within 48 hours** of receipt.
- **Triage decision within 14 calendar days** — we will tell you whether
  we accept the report, classify the severity, and give a target window
  for the fix.
- We will not pursue legal action against good-faith research that
  follows this policy and avoids data destruction, privilege escalation
  on infrastructure we do not own, or social engineering of users.
- Please do not publicly disclose before we have shipped a fix or the
  14-day triage window has lapsed without a response.

## Threat model — demo deploy

This is the model for the hackathon demo, not for a production tenant.
It will be revised before any real customer data lands.

**In scope** (we own these and will fix issues):

- Hausbuch application code in this repository
- Production npm dependencies declared in `package.json`
- The CI configuration in `.github/workflows/`
- Server-side handling of API keys (must stay in environment, must not
  cross the network boundary to the browser)

**Out of scope** (we monitor but cannot directly patch):

- Upstream SaaS providers we integrate with (Google Gemini, Tavily,
  Aikido, Gradium). Issues are reported upstream.
- Cloud, DNS, and CDN infrastructure underneath the demo deploy.
- Browser, OS, and network-layer attacks against an end user's machine.

## Known risks in the hackathon build

We are honest about the rough edges. None of the following are bugs;
they are deliberate trade-offs for a public demo with public sample
data. Each one will tighten before any real tenant onboards.

- **Demo data is public.** The buildings, leases, emails, and tickets
  in `samples/` are synthetic. Anything you upload to the live demo is
  treated as public. Do not upload real tenant data.
- **No auth on `/audit`.** The action log is intentionally readable by
  anyone with the demo URL — judges need to be able to verify nothing
  happens silently. A real deploy will gate this behind tenant auth.
- **API keys live in server env only.** `GEMINI_API_KEY`,
  `TAVILY_API_KEY`, and any partner credentials are read from
  `.env.local` on the server. They are never sent to the browser, never
  echoed in HTML, and never returned in API responses. `.env.local` is
  gitignored (see `FR-29` in the PRD).
- **No rate limiting on public endpoints.** The demo is not protected
  against burst traffic; partner API quotas absorb this in practice.

## Log redaction (FR-30)

Tool-call logs (every external LLM and partner API call) must redact
API keys, OAuth tokens, and PII before persistence. This is **pending,
scheduled for Phase 3** alongside the rest of the action log work
(FR-7, FR-8, FR-10). Until that lands, the action log is not yet
written to durable storage in a form that would expose secrets — but
the redaction layer is the right place to enforce this and is on the
list.
